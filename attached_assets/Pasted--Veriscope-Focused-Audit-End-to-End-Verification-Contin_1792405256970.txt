1. Upload a supported PDF or document.
2. Confirm text extraction works and errors are handled clearly.
3. Confirm risk analysis returns meaningful findings grounded in the original document.

5. Confirm the risk register and review flags display the analysis correctly.
6. Add new evidence and reassess an existing open risk.
7. Confirm conflicting, insufficient, or promise-only evidence cannot automatically close a risk.
8. Confirm that closing a risk still requires human approval.
9. Confirm risk detail responses remain consistent.

Use existing tests and mock-based verification wherever possible. Do not repeat real provider calls that have already been proven unless a specific regression makes one necessary.

### 2. Check only the most important security issues

Perform a focused check for:

- Unauthorized access to another user's documents or risks, if user separation exists.
- Ability to close risks without the required human approval.
- Unsafe file uploads that could crash the application or bypass expected validation.
- Exposed API keys, secrets, or sensitive error details.
- Endpoints that can trigger uncontrolled or repeated paid AI calls.

Report other observations only if they represent a concrete and relevant risk. Do not spend excessive time on theoretical issues or comprehensive enterprise security hardening.

For each confirmed issue, state:
- Severity
- Affected file or route
- Reproducible scenario or supporting code evidence
- Practical impact
- Smallest reasonable fix

Clearly distinguish verified vulnerabilities from potential concerns. Passing tests alone does not prove security.
